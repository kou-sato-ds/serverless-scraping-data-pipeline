# ADR-014: ウォーターマークを S3 に保存し、成功後にだけ前進させる

| 項目 | 内容 |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-09-25 |
| **関連 PR** | PR #22 (incremental-fetch) |
| **Ports** | 姉妹プロジェクト item 106 |

## 1. 背景

ADR-002 の冪等キーにより、同じ記事を何度書いても S3 の最終状態は変わらない。

## 2. 問題

**「壊れない」ことと「無駄がない」ことは別である。**
毎時フィード全件を PUT し直せば、リクエスト課金を記事数に比例して払い続ける。

そして Lambda は状態を持てない。「前回どこまで取ったか」を保持する場所が無い。

## 3. 決定

ウォーターマークを `state/incremental_watermark.json` として S3 に保存する。

| 原則 | 防ぐ事故 |
|---|---|
| `>=` と lookback 2時間で多めに読む | 遅延到着・同時刻の取りこぼし |
| アップロード成功後にだけ保存 | 失敗区間の永久欠落 |
| 後退させない | 読み取り範囲の膨張 |
| `published` 無しの記事は含める | 判定不能による取りこぼし |

### なぜ多めに読んでよいか

重複して取得しても、ADR-002 のキーで同じ S3 オブジェクトに収束する。
**取りこぼすより、重複を冪等に吸収する方が安い。**

### なぜ NoSuchKey 以外を握りつぶさないか

権限エラーを「初回」と誤認すれば、毎回全件を取り直す状態が静かに続く。
ADR-003 の「例外を握りつぶさない」と同じ判断である。

## 4. 結果

### ポジティブ
- 取得済み区間の再 PUT が減る
- 失敗しても次回同じ区間を読み直す

### ネガティブ / 残課題
- `lambda_handler` への組み込みは後続 PR
- 並行実行時の競合（2つの実行が同時に状態を更新）は未対処。現状は同時実行1を前提とする

## 5. 教訓

**冪等性は安全を保証するが、効率は保証しない。**
ADR-002 で「何度書いても壊れない」を作り、本 ADR で「何度も書かない」を足した。
