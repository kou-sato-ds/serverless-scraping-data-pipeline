# ADR-012: スキーマ変更を互換性で分類し、バージョン番号と一致させる

| 項目 | 内容 |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-09-21 |
| **関連 PR** | PR #18 (schema-compatibility) |
| **Ports** | 姉妹プロジェクト item 105 |

## 1. 背景

`src/app.py` には `SCHEMA_VERSION = "2.0"` という定数があるが、
**これが上がったときに何が起きるかが定義されていない**。

## 2. 問題

S3 には過去のバージョンで書かれた JSON が残り続ける。
Athena でクエリすれば新旧が同じテーブルとして読まれ、
列が増えていれば古い行は NULL、型が変われば読み取りが落ちる。

そして BigQuery と違い、**S3 + Athena にはスキーマ強制が無い**。

| タイミング | 何が起きるか |
|---|---|
| 書き込み時 | 何のエラーも出ない。壊れた JSON もそのまま保存される |
| クエリ時 | 初めて露見する。しかも「誰かがクエリしたとき」 |

ADR-010 で「エラーにならない異常が最も長く放置される」と書いたが、
スキーマ不整合はその典型である。

## 3. 決定

`src/schema.py` に以下を実装する。

| 関数 | 役割 |
|---|---|
| `validate_payload()` | 書き込み前に必須フィールドを検証 |
| `classify_payload_change()` | 変更を後方互換/破壊的に分類 |
| `decide_version_bump()` | 破壊的変更にメジャー昇格が伴うか判定 |

### なぜバージョン番号を検証するか

**メジャーが上がる = 破壊的変更を含む、という約束**である。
この約束を守らなければ、バージョン番号は単なる飾りになる。

下流は「2.x なら読める」という前提でクエリを書く。
破壊的変更を 2.1 として出せば、その前提が静かに破られる。

### なぜ例外を投げないか

1 件の不備でバッチ全体を落とせば、正常な記事まで届かなくなる。
ADR-003 の DLQ が「壊れたものだけ隔離し、他は通す」のと同じ思想。

## 4. 結果

### ポジティブ
- 破壊的変更をバージョン据え置きで出せば検知される
- 書き込み前にペイロードの不備が分かる

### ネガティブ / 残課題
- **既存の S3 データへの遡及適用は未実装**。
  過去分の検証は別途バッチが要る
- 分類できるのはトップレベルのみ。`article` 内部のネストは対象外

## 5. 教訓

**スキーマ強制の無いストレージでは、書き込む側が責任を持つ。**

BigQuery なら型違反は INSERT が落ちる。S3 は何も言わない——
だから「エラーが出ていない」は「正しい」を意味しない。
ADR-010 の「パースは通るが異常なデータ」と同じ構造が、
スキーマの層にも存在する。
