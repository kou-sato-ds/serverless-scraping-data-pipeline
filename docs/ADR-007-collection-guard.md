# ADR-007: テストスイート自身に健全性ガードを持たせる

| 項目 | 内容 |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-08-13 |
| **関連 PR** | PR #12 (collection-guard) |
| **Implements** | ADR-006 §5 再発防止策 |

## 1. 背景

ADR-006 に記録した通り、`tests/test_app.py` に構文エラーが混入し、
テストが1件も collect できない状態が2日間 main に残った。

## 2. 問題

既存の CI 設定には `--cov-fail-under=90` があったが、これは機能しなかった。
**テストが0件ならカバレッジ計算に到達せず、collection error で終わる**ためである。

つまり「カバレッジが下がったこと」は検知できるが、
**「テストそのものが消えたこと」を検知する仕組みが無かった**。

## 3. 決定

テストスイート自身が自分の健全性を検証する
`tests/test_collection_guard.py` を追加する。

| STAGE | 検証内容 |
|---|---|
| 1 | `test_app.py` が構文的に正しいこと（`ast.parse`） |
| 2 | テスト件数が下限（40）を割っていないこと |
| 3 | 全テストファイルが parse できること |
| 4 | 文字化け（ADR-005 の事故パターン）が無いこと |

### なぜ pytest の設定ではなくテストで解くか

`--cov-fail-under` のような設定値は、**異常時に評価されないことがある**。
テストとして書けば、pytest が collect できる限り必ず実行される。

**「壊れた時に動かない防御」より「壊れても動く防御」を選ぶ。**

## 4. 結果

### ポジティブ
- テストが消えた瞬間に、明示的なメッセージ付きで失敗する
- 文字化け（ADR-005）も同じ仕組みで検知できる

### ネガティブ / 残課題
- `MINIMUM_EXPECTED_TESTS` は手動更新が必要
- ガード自身が壊れたら検知できない（この再帰は原理的に断ち切れない）

## 5. 教訓

**監視の設計では「異常時にも動くか」を問う**。

`--cov-fail-under=90` は正常時には機能するが、
最も知りたい異常時（テスト0件）には到達しない。
ADR-006 で「常に赤いワークフローが赤信号の意味を奪った」と書いたのと同じ構造——
**動かない防御は、無いのと同じではなく、有ると錯覚させる分だけ悪い**。

### 実装時の発見: ガードは自分自身を除外する

初回実装では、モジバケ検知パターンを `parametrize` に直接書いたため、
**ガード自身がそのパターンを含み、自分を誤検知して失敗した**（4 failed）。

検査対象から自分自身を除外し、パターンを Unicode エスケープ（`\u7e67` 等）で
保持することで解決した。監視を実装する際は
**「監視対象に監視自身が含まれていないか」**を必ず確認する。
