# ADR-009: 想定問答をコードとして持ち、根拠の実在をテストで守る

| 項目 | 内容 |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-08-27 |
| **関連 PR** | PR #15 (interview-narrative) |
| **Ports** | 姉妹プロジェクト item 92 |

## 1. 背景

ADR-008 で README に ADR 索引を置き、「どこを読むか」を示した。
しかし**「これをどう語るか」がどこにも無い**。

姉妹プロジェクト Mastering-Data-Engineering-Foundations の item 92 で
同じ課題に対処したが、**その6問のうち4問は本リポジトリの実装を語っている**——
にもかかわらず、こちら側には問答が無い状態だった。

## 2. 問題

口頭説明は準備しなければ崩れる。特に「なぜその設計を選んだか」を
実装を見ながらでないと答えられないなら、それは理解していないのと同じである。

そして**想定問答は最も腐りやすいドキュメントでもある**。
実装が変われば説明は古くなるが、文書に書いただけでは誰も気づかない。

## 3. 決定

想定問答を `tests/test_interview_narrative.py` にコードとして持ち、
各回答に **ADR 番号（evidence）** を伴わせる。

| 検証 | 内容 |
|---|---|
| STAGE 1 | 引用した ADR が実在すること |
| STAGE 5 | **全 ADR が少なくとも1つの問答でカバーされること** |
| STAGE 4 | 回答が60字以上あること |
| STAGE 7 | 核心の関心が問答を持つこと |

### なぜ STAGE 5 を双方向にするか

ADR-008 と同じ構造である。片方だけの検証では乖離が残る。

- 問答が実在しない ADR を引用 → 聞き手が確認しようとしても見つからない
- ADR を書いたが語る準備が無い → **記録した意味が半減する**

**書いた設計判断は、説明できて初めて資産になる。**

## 4. 結果

### ポジティブ
- ADR を追加して問答を用意し忘れれば CI が赤くなる
- 面接前に「何を語れて何を語れないか」が機械的に分かる

### ネガティブ / 残課題
- 回答の**正確さ**は検証できない（長さと参照の実在のみ）
- 実際に口頭で言えるかは、別途練習が必要

## 5. 教訓

**作ったものは、語れて初めて伝わる。**

ADR-008 で「書いたものは辿れて初めて価値になる」と書いたが、
その先がある——辿り着いた読者に説明できなければ、
索引も ADR も本人の理解を証明しない。

量を増やすより、**説明できる範囲を増やす**方が転職市場では効く。
