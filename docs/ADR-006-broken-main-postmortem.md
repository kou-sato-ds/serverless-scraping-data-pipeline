# ADR-006: 構文エラーが main に到達した経緯と再発防止

| 項目 | 内容 |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-08-11 |
| **関連 PR** | PR #9 (hotfix), PR #10 (closed) |

## 1. 何が起きたか

PR #6 のマージ後、`main` の `tests/test_app.py` に構文エラーが含まれていた。

    def  None():

`lambda_context` フィクスチャの定義名が `None` に置換された状態でマージされ、
**テストが1件も collect できない**まま2日間 main に残った。

## 2. なぜ起きたか

PR #4 の作業中、無関係な編集を戻すために `, lambda_context)` → `, None)` の
一括置換を行った。この置換が意図した呼び出し箇所だけでなく、
**フィクスチャの定義名そのもの**にも適用された。

置換後にテストを再実行しなかったため、壊れた状態でコミット・push・マージされた。

## 3. なぜ気づけなかったか

CI は赤かったが、その原因を **`--cov-fail-under=90` だと推測**していた。
実際には collection error でテストが0件だった。

さらに、学習ログリポジトリからコピーされた `.github/workflows/ci.yml` が
本プロジェクトの依存をインストールせず常に失敗していたため、
**「CI が赤いのは ci.yml のせい」という誤った説明が成立してしまい**、
本当の赤の原因が隠れた。

## 5. 再発防止

1. **一括置換の後は必ずテストを実行してからコミットする**。
   置換は意図しない箇所に届く前提で扱う。
2. **CI が赤い時、推測で原因を決めない**。必ずログの該当行を読む。
   本件では `SyntaxError` の1行が最初から出ていた。
3. **常に失敗するワークフローを放置しない**。
   「いつも赤いもの」があると、本物の赤が埋もれる。

## 6. 教訓

**壊れたことより、壊れたと気づけない仕組みの方が危険である**。

テストは 43 件あり、CI も動いていた。しかし
「常に赤いワークフロー」が1つ紛れ込んだだけで、
**赤信号が意味を失った**。監視は数を増やすほど強くなるのではなく、
**信頼できない信号を1つ持つだけで全体が弱くなる**。
