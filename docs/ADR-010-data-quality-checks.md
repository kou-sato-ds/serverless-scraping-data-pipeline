# ADR-010: パースは通るが異常なデータを検知する

| 項目 | 内容 |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-09-06 |
| **関連 PR** | PR #16 (data-quality) |
| **Ports** | 姉妹プロジェクト item 97-99 |

## 1. 背景

ADR-003 で例外伝播と SQS DLQ を導入したが、それが捕まえるのは
「取得に失敗した」場合だけである。

## 2. 問題

RSS フィードが正常に返ってきているのに、中身が劣化しているケースは
一切検知できない。

| 事象 | 現在の挙動 |
|---|---|
| title が空文字の記事が大量に混じる | S3 へそのまま書き込まれる |
| 同一 link が重複配信される | 同じキーへ収束するが兆候は残らない |
| published が全欠落 | パーティションが fetched_at に寄り、時系列が歪む |
| 記事数が普段の 1/10 | 正常終了として扱われる |

いずれも feedparser はエラーを出さず、DLQ にも落ちず、
**Athena のクエリは静かに歪んだ結果を返す**。

## 3. 決定

`src/quality.py` に検証ロジックを実装し、
`lambda_handler` から呼んで**構造化ログへ記録する**。

### なぜ処理を止めないか

品質チェックは処理を止めるためではなく、記録するためのものである。

タイトルが 2 割欠けていても、残り 8 割は分析に使える。
ADR-003 の DLQ が「壊れたものだけ隔離し、他は通す」のと同じ思想を、
バッチ全体の品質にも適用する。

### なぜ例外ではなくログか

例外を投げれば ADR-003 のリトライが発動するが、
**フィードの中身が劣化しているならリトライしても同じ結果になる**。
リトライで解決するのは一時的な障害だけである。

## 4. 結果

### ポジティブ
- Logs Insights で `filter quality_issue_count > 0` により劣化を追える
- 正常時もログを出すため、無音が「正常」か「未実行」かを区別できる

### ネガティブ / 残課題
- 閾値がコードに埋め込まれている。CloudWatch メトリクス化は後続 PR
- 過去との比較（記事数が「普段の」1/10 か）は未実装。
  現状は固定の下限値のみ

## 5. 教訓

**エラーにならない異常が、最も長く放置される。**

ADR-006 で「常に赤いチェックは赤信号の意味を破壊する」と書いたが、
その逆もある——**信号そのものが上がらない異常**である。
DLQ に落ちず、例外も出ず、クエリも成功する。
だから明示的に測らなければ、誰も気づかない。
