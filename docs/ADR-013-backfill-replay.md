# ADR-013: バックフィルを「失敗した時間帯の再生」として設計する

| 項目 | 内容 |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-09-22 |
| **関連 PR** | PR #21 (backfill-replay) |
| **Ports** | 姉妹プロジェクト item 103 |

## 1. 背景

姉妹プロジェクトの item 103 でバックフィル計画を実装した。
BigQuery 側では「過去の日付範囲を作り直す」ことができる。

## 2. 問題

本パイプラインの入力は Google News RSS であり、**「今」の記事しか返さない**。
過去のフィードは取り直せない。GCP 側と同じ意味のバックフィルは成立しない。

## 3. 決定

バックフィルを **「失敗した時間帯の Lambda 実行を、同じ形のイベントで再生する」**
と定義し、`src/backfill.py` で再生計画を構築する。

| 要素 | 設計 |
|---|---|
| 単位 | 毎時スロット（EventBridge の実行単位と一致） |
| 上限 | 72 時間 |
| 同時実行 | 3 まで |
| イベントID | スロット時刻から決定的に導出 |

### なぜ安全に再生できるか

- **ADR-002**: S3 キーが記事内容から導出される。再実行しても重複しない
- **ADR-005**: 相関IDが `event['id']`。同じスロットは同じIDになり、元の試行と束ねて追跡できる

**冪等性と観測性を先に作っておいたことが、ここで初めて実利になる。**

### なぜイベントIDを決定的にするか

ランダムな ID にすると、再生のたびに別の実行としてログに現れる。
同じ時間帯の試行が散らばり、「この時間帯は結局成功したのか」が追えなくなる。

## 4. 結果

### ポジティブ
- 失敗した時間帯を、計画・上限・同時実行制限付きで再生できる
- 再生は元の実行と同じ S3 キーに収束する

### ネガティブ / 残課題
- **RSS から消えた記事は復旧できない**。再生で取れるのは「その時点でまだフィードにある記事」のみ
- 完了判定（どのスロットが成功したか）の取得元は未実装。現状は呼び出し側が渡す

## 5. 教訓

**同じ言葉でも、データソースが違えば意味が変わる。**

GCP 側の「バックフィル」は過去データの作り直しだが、
RSS を入力とする本パイプラインでは「失敗の再生」にしかならない。
横展開は、設計をそのまま写すことではなく、
**制約に合わせて意味を翻訳すること**である。
